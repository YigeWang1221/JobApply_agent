# 设计：投递追踪、招聘轮次、Dashboard 与面试复盘

状态：**已确认**（2026-10-22）；未施工。日期：2026-10-22。

主流程见 [workflow.md](workflow.md)。storage 结构见 [memory.md](memory.md)。

## 用户需求（2026-10-22）

- 台账的栏目要重新设计。不同公司的招聘流程不一样，投递之后可能有很多轮面试。
- 每个 Project 有一个大 Dashboard，可以是类似 Linear 的看板，也可以是别的图形。要能看出：投了多少、多少家公司走到了哪个阶段、多少还没有追踪。
- 系统不只管投递，还管后续：面试经过、考了什么、遇到什么问题、经验总结。
- 例：某个 Session 投了公司 X，进了一面。用户面试回来后在 Session 里和 AI 聊一面的情况，AI 把结果更新到台账和 Memory。日后复盘时，能按「X 一面复盘」「X 二面复盘」「X 三面挂了」找到记录，也能在「常考题」里找到这些题目。

## 核心思路：固定的「阶段」加上可变的「轮次」

公司之间的流程差异很大：有的公司只有一面加 HR 面，有的公司有笔试加五轮面试。所以拆成两层：

| 层 | 是什么 | 取值 | 用途 |
| --- | --- | --- | --- |
| **阶段 `phase`** | 所有公司都一样的大阶段 | 固定枚举（见下） | 台账分组、看板列、漏斗图。所有公司可以横向比较 |
| **轮次 `rounds`** | 这家公司实际发生的每一轮 | 可变列表，发生一轮就追加一轮 | 记录面试详情和复盘，展示进度 |

### 阶段（固定）

```text
prep        准备中（选岗、填写、待审核）
applied     已投递（有提交证据）
screening   简历筛选中
assessment  笔试 / OA / 测评
interview   面试中（不管第几轮）
offer       Offer 阶段（口头、书面、谈薪）
closed      已结束
```

`closed` 一定带结局 `outcome`：

| outcome | 含义 |
| --- | --- |
| `accepted` | 接受 Offer |
| `declined` | 拒绝 Offer |
| `rejected` | 被拒（记录挂在哪一轮） |
| `withdrawn` | 主动撤回 |
| `ghosted` | 长期无回应，由用户手动确认后关闭 |
| `not_submitted` | 准备了但最终没有投 |

`phase` 由轮次**自动推导**：最新一轮是笔试，阶段就是 `assessment`；是面试，就是 `interview`；出现 Offer 轮，就是 `offer`。轮次的结果是 failed，或者用户关闭申请时，阶段变为 `closed`。用户也可以手动改阶段，事件日志里会记一条。

原先 design 里的细粒度状态（`needs_input`、`needs_login`、`awaiting_review`、`verification_pending` 等）只在 `prep` 阶段内部使用，作为子状态 `prep_state`，不出现在 Dashboard 的大分组里。

### 轮次（可变）

每一轮是一条记录：

| 字段 | 说明 |
| --- | --- |
| `seq` | 第几轮（1, 2, 3…），按实际发生顺序编号 |
| `name` | 公司的叫法，例如「一面」「技术二面」「Onsite Loop 1」「HR 面」 |
| `type` | 归类，便于统计：`screen-call` / `oa` / `written-test` / `assessment` / `technical` / `coding` / `system-design` / `behavioral` / `manager` / `hr` / `final` / `offer-call` / `other` |
| `scheduled_at` / `happened_at` | 约定时间 / 实际时间 |
| `format` | 线上 / 线下 / 电话；时长 |
| `interviewer_role` | 只记角色，例如「组内工程师」「部门主管」。**默认不记面试官姓名** |
| `result` | `pending` / `passed` / `failed` / `cancelled` / `unknown`（用户未同步，见下方「unknown 规则」） |
| `result_at`、`result_source` | 结果来源：`portal`（官网状态）/ `email` / `recruiter`（HR 告知）/ `user`（用户自述） |
| `review` | 指向该轮复盘文件 |
| `question_count` | 这一轮记了几道题 |

### unknown 规则（用户已确认，2026-10-22）

投递之后的状态**只来自用户在 Session 里的手动回复**（官网能查到时顺带核验）。系统不推断结果，不按阶段设不同的阈值。

- 一个事件该有下文、但用户 7 天内没有同步时，标记为 `unknown`，含义是「用户未同步」，不等于被拒或没有回应。具体情况：
  - 某一轮的 `scheduled_at` 已过 7 天，结果仍是 `pending`，这一轮的 `result` 记为 `unknown`；
  - 已投递后 7 天内没有任何更新，申请标记为 `unknown`。
- 阈值全局只有一个，默认 7 天，可以在 Project 偏好里修改。
- 用户回复后，`unknown` 就被真实结果替换；事件日志会保留「曾经是 unknown」的记录。
- `ghosted`（长期无回应）只能由用户手动关闭时选择，系统不会自动设置。
- Dashboard 的「待追踪」就是所有 `unknown` 的项。

**公司流程模板**：`companies/<company>.md` 里可以记录「这家公司通常有哪几轮」，来源可以是官网说明、HR 告知，或者以往的经历。有模板时，看板上会显示预计的剩余轮次，用空心圆表示；没有模板时，只显示已经发生的轮次。模板只用来展示预期，**不代表**真实情况，真实轮次以实际发生的为准。

## Dashboard（每个 Project 一个，另有全局一个）

属于前端的正式页面（施工第 6 段）。数据由后端 API 从 Job 记录计算得出，另外生成一份 `dashboard.md` 快照，供 AI 和用户在命令行里阅读。

```text
├──────────────────────────────────────┴───────────────────────────────┤

├──────────────────────────────────────┬───────────────────────────────┤
│ ⑥ 每周节奏：投递数 / 面试数（柱状图）     │ ⑦ 复盘概览：常考题主题 Top N、     │
│                                       │    各轮次挂掉的分布                │
└──────────────────────────────────────┴───────────────────────────────┘
```

| 组件 | 回答的问题 | 计算方式 |
| --- | --- | --- |
| ① KPI 卡 | 投了多少、涉及多少家公司、各阶段各有多少 | 按 `phase` 计数；「公司」按公司去重 |
| ② 漏斗 | 多少家公司走到了哪一步 | **按公司数统计**（用户已确认）：每家公司各申请里走得最远的那一层就是它的位置，一家公司在每一层最多算 1 次。统计的是「曾经到达过」这一层的公司数，不是当前停在这一层的数量。层级是固定阶段加上轮次序号（一面、二面…）。旁边可以显示每层的申请数作为参考，因为各公司允许投的岗位数不同 |
| ③ 看板 | 每个申请现在在哪 | 列等于 `phase`。**看板只读**（用户已确认）：状态只能通过在 Session 里回复来更新，并写进事件日志 |
| ④ 待追踪 | 哪些用户还没同步 | 所有 `unknown` 的申请和轮次，见「unknown 规则」 |
| ⑤ 时间线 | 每个申请的节奏 | 投递日、各轮的 `happened_at`、结果 |
| ⑥ 每周节奏 | 投递和面试是否均衡 | 按周统计 |
| ⑦ 复盘概览 | 哪些主题常考、常在哪一轮挂掉 | 来自轮次和题库 |

图表实现时遵循 dataviz 规范（施工时再定具体图表库）。

## 投递之后：在任意 Session 里更新

一个 Job 的生命周期覆盖**从候选到结束的整条申请**，跨多个 Session（见 [memory.md](memory.md)「修订：Session 与岗位解耦」）。投递之后，用户可以回到原来的 Session，也可以新开一个 Session 来聊。Agent 根据对话内容识别是哪个 Job（有歧义时，比如同一家公司投了两个岗位，会先问清是哪一个）。例如：

> 「X 的一面刚结束，问了限流器设计和一道 LRU，感觉第二题写得不好，面试官说一周内通知。」

Agent 的处理：

1. **识别出这是一轮面试的更新**，起草两份内容：
   - 轮次记录：一面、technical、今天、结果 pending；
   - 复盘草稿：问题列表（每题打上主题标签）、你的作答要点、自评、面试官的反馈和追问、教训。
2. **展示草稿并让用户确认**，用户可以修改、补充。
3. **确认后写入**：轮次表、Session 阶段（自动推导为 `interview`）、下一件事（等通知，提醒日期为一周后）、题库。
4. **提出 Memory 候选**。例如「公司 X 的流程比模板多一轮」写进公司记忆，「系统设计题要先问清 QPS」作为经验候选写进 lessons。

用户回报「二面挂了」时：这一轮的 `result` 改为 `failed`，`phase` 改为 `closed`，`outcome` 改为 `rejected`，并记录挂在第几轮。Agent 会主动问一句要不要做失败复盘。

**结果来源要标注**：面试结果大多只能由用户告知（`result_source: user`），这一点和投递环节「必须有官网证据」不同。官网状态能查到时，会在追踪时顺带核验一次。

## 面试复盘与常考题

### 放在哪里

| 内容 | 位置 | 理由 |
| --- | --- | --- |
| 某一轮的复盘（原始记录） | `projects/<p>/jobs/<job-id>/rounds/<seq>-<type>.md` | 跟着申请走，是原始事实，**只有这里是用户确认过的手写内容** |
| 常考题库 | `storage/review/questions.md`（生成） | 题目和人有关、和侧重无关，所以跨 Project 汇总；每题标注出处 |
| 按公司汇总 | `storage/review/companies/<company>.md`（生成） | 再投同一家公司，或者面试前复习时用：这家公司历次各轮问过什么 |
| 经验总结 | `storage/review/lessons.md` | 从各轮复盘里提出的候选，经用户确认后写入；带来源链接 |
| 公司流程观察 | `companies/<company>.md` | 轮次模板、平均间隔、HR 习惯 |

**这样「X 一面复盘」「X 二面复盘」「X 三面挂了」三种查法都有着落**：
- 原始复盘在各自 Session 的 `rounds/` 下；
- 按公司汇总看 `review/companies/X.md`；
- 按题目复习看 `review/questions.md`。

后两份是生成文件，只有原始复盘需要你确认。

### 轮次复盘文件格式

```markdown
---
job: 2026-10-16-003
session: <记录这一轮的那个 Session>
company: 公司 X
round: { seq: 1, name: 一面, type: technical }
happened_at: 2026-10-18T14:00+08:00
format: 线上 60 分钟
interviewer_role: 组内工程师
result: passed
result_source: user
---

## 经过
（简述）

## 题目
### Q1 · 设计分布式限流器
- topic: [system-design, rate-limiting]
- canonical: q-rate-limiter          # 归并到题库中的同一道题
- 我的作答：令牌桶 + Redis 计数……
- 自评：没讲到多机时钟漂移
- 追问：如何应对热点 key？
- 复习状态：todo                      # todo / reviewed / mastered

### Q2 · LRU Cache（手写）
- topic: [coding, data-structure]
- canonical: q-lru-cache
- …

## 面试官反馈
## 教训（候选）
- 系统设计先问清 QPS 和一致性要求再动笔
```

### 题库（生成）

`review/questions.md` 按主题分组，每道归并后的题目（`canonical`）显示以下信息：

- **出现次数**：被问过几次，这就是「常考」的依据；
- **出处列表**：哪家公司、第几轮、哪个 Project，并链接到原始复盘；
- **最近的复习状态**。

主题按出现次数排序。归并时，Agent 会建议「这题和 `q-rate-limiter` 是同一道」，由用户确认后写入 `canonical`。

### 隐私

- 复盘只存在本地，不进 Git，不发给外部服务（与 `dev-limit.md` 一致）。
- 默认不记录面试官姓名和联系方式。
- 有的公司要求候选人对面试题保密，是否记录由用户自行判断。
