# 设计：求职投递主流程

状态：**已确认**（2026-10-22）；未施工。日期：2026-10-22（已按旧工作区复盘修订）。

产品目标见 [base.md](base.md)。Project / Session 与 storage 结构见 [memory.md](memory.md)。旧流程经验见 [research-codex.md](../reference/research-codex.md)。目录见 [architecture.md](architecture.md)。

## 一句话

在类似 Claude 的界面里，用户在某个 Project（一种求职侧重）下开 Session：系统按该 Project 的个人资料和偏好找到匹配岗位，通过 Chrome MCP 在浏览器里代填申请表，**在提交前停下来交给用户审核，最终提交由用户本人点击**，然后只读核验官网结果，写入本地台账，并跟踪进度和最近一次查询时间。

设计偏重 MCP：浏览器操作走 Playwright MCP；搜索和抓取的接法待定（倾向后端直接调 API，见「三种接法的区别」）；自研 Tool 负责 Memory、台账、材料和额度。

## 主流程（一个 apply Session）

用户已确认的顺序（2026-10-22）：**打开申请页 → 交给用户登录 → 岗位核实 → 简历补全（填写） → 提交前交给用户审阅 → 用户手动提交 → 审阅通过后做本地流程优化和内容更新。**

```text
[恢复状态] → [资格与额度（基于候选池里已有的 JD 快照）] → (关卡 A：选岗 + 确认材料包)
  → [打开申请页] → (接力：用户登录，每次申请都交给用户) → [身份核对]
  → [岗位核实：在已登录页面上核对岗位、ID、城市、额度提示、筛选题]
  → [上传主简历 → 等解析 → 校正字段] → [逐页填写 ⟲：Agent 能填的统一填完]
        ├─ 未知问题 → (集中问答：needs_input)
        └─ C 级字段 → (接力：用户亲填)
  → [保存并回读核验] → (关卡 B：用户审阅填写报告与页面，图暂停，标签页保持打开)
  → 用户在 Chrome 里自己点提交（如果出现安全验证，也由用户完成）
  → [只读核验官网结果] → [写入 Job 记录与台账（md + csv）]
  → [流程优化与内容更新：提出 Playbook / Memory 候选 → 用户确认 → 写入]
  … 之后用户在 Session 里回复进展 → 更新轮次与 last_checked_at
```

| 节点 | 做什么 | 能力 |
| --- | --- | --- |
| 恢复状态 | 读取 Project 的有效资料（base + overrides 解析后）、相关 Playbook、公司记忆、本 Session 的 Checkpoint。只读当前任务需要的部分 | 自研 Tool |
| 岗位核实 | 完整读一次官方 JD：岗位名、ID、城市、类型/届别、资格原文（保留 AND/OR/equivalent）、截止日期、薪资（未披露就写未披露） | 已登录页面用浏览器只读；候选阶段的 JD 快照来自搜索层的抓取 |
| 资格与额度 | 硬门槛检查；评分；查跨 Project 的历史投递，避免重复；查公司额度（未核实就写未核实） | 自研 Tool + 模型 |
| 关卡 A | 一次性展示：岗位、链接、资格结论与风险、额度、拟用简历和附件。用户确认即授权本岗位（或明确列出的批次）的**填写**，不是授权提交。B 级个人信息不在这里逐项确认，统一填完后在关卡 B 审核 | LangGraph4j 暂停 / 恢复 |
| 用户登录（接力） | 打开申请页后**每次都交给用户**：用户在 Chrome 里登录（或确认已登录），然后通过本地 HTTP 接口发送 `logged_in` 信号（以后前端复用这个接口），由模型读快照判断是否已登录。模型可能判断错，所以用户可以 override 强制继续，每次都留审计事件（用户确认，2026-10-22；C004 起 override 的意义从「识别规则误判」改为「模型判断错了」） | 暂停 / 恢复 |
| 身份核对 | 读取页面上可见的账户名和官方投递历史，核对是不是正确的账号（防止多个账号混淆）；不读取 Cookie | Chrome MCP |
| 上传与解析 | 遇到上传位置时，先列出 `base/assets.md` 里登记的原件问用户要上传哪些，用户也可以当场拖入新文件（登记后再选），选定的写进 `job.md` 的 `materials`（用户确认，2026-10-22）；先上传主简历，等解析完成，再按资料校正被覆盖或识别错的字段；按授权关闭「同步更新在线简历」类选项 | Chrome MCP |
| 逐页填写 | 快照 → 批量填 A/B 级字段 → 选择 / 上传 → 点「下一步」类按钮；页面变化后重新取快照 | Chrome MCP（Harness 循环） |
| 集中问答 | 把本页及已知的未知必填项合并成一张清单，保留原文和选项，一次问完 | 暂停 / 恢复 |
| 接力 | Agent 停止写操作，用户在浏览器里操作；用户交回后，Agent 先重新取快照、只读核对，不覆盖用户填的内容 | 暂停 / 恢复 |
| 保存并回读 | 保存后刷新或重新进入页面，回读关键字段、附件名与大小、已选城市标签 | Chrome MCP |
| 关卡 B | 生成填写报告：每个字段的值、**来源层**、置信度，C 级字段只标注「用户已填」，附件清单，未解决的问题 | 暂停 / 恢复 |
| 只读核验 | 用户说已提交后，读成功页和官方历史，记录官网原文、官网时间和本地时间；没有证据就不记为已提交 | Chrome MCP |
| 写入台账 | 更新 `job.md` 和事件日志，重新生成本 Project 的 md 台账和 csv | 自研 Tool |
| 流程优化与内容更新 | 用户审阅通过后，从本次过程中提出候选：站点 skill 的修补、通用经验、个人事实。用户确认后写入。规则见下方「流程优化的安全边界」 | 模型 + 自研 Tool |

上面是**一个 Job 的申请流程**（申请线程，thread id = job id），可以跨多个 Session 暂停和继续。调研是另一条流程：按 Project 偏好搜索 → 核实 → 打分 → 写入候选池。一个 Session 里可以只做调研、调研加投递，或者只推进已有的申请，见 [memory.md](memory.md)「修订：Session 与岗位解耦」。

## 流程优化的安全边界

用户问：每次申请后做流程优化，会不会对 Agent 造成不好的影响？会有风险，所以要限定它能改什么。

| 可能的坏影响 | 例子 | 防护 |
| --- | --- | --- |
| **改坏安全规则** | 某次复盘得出「这个站点的『投递』按钮其实只是下一步」，于是放开了拦截 | 提交守卫的硬边界**写在代码里**（词表也在代码里），不在 Playbook 里，流程优化碰不到，只能由开发修改。站点记录只能追加「你确认过的软边界按钮」，而且这类记录放行不了硬边界的按钮 |
| **规则膨胀、互相矛盾** | 旧工作区的 `WORK_BY_STEPS.md` 涨到约 29KB，同一段内容出现在多处 | 每个文件设字符预算；优先修补已有条目，不新建；写入前检查是否与已有规则冲突，有冲突时交给你选 |
| **以偏概全** | 一个站点的特例被写成通用规则 | 站点特有的事实先写进 `playbook/sites/<host>.md`（不是 skill）；可以复用的经验修补对应的组件或平台 skill（`observed_count` 计数）；在 ≥2 类站点上出现过、经你同意后，才写进通用的 `apply-form` skill |
| **网页内容混进规则（提示注入）** | JD 或页面里藏着「忽略之前的规则」之类的文字，被当作经验写进去 | 候选写入前做注入和不可见字符检测；候选只能来自 Agent 自己的观察，不能原样摘抄网页文字 |
| **越改越差但没人发现** | 新规则让填写变慢、出错更多 | 开启 git 时，`storage/.git` 每次写入自动提交，可以回滚到任意版本（git 是可选项，不开启就不能回滚）；施工第 3 段的 HTML 夹具测试每次改动后都重跑，确认守卫和填写行为没有退化 |
| **个人信息被写成默认** | 一次申请里的城市排序、专业写法被当成通用事实 | 作用域分层：单次申请的答案默认只留在这个 Job 里，升级到 Project 或 base 必须你确认 |

结论：在这些边界内，流程优化**只能影响效率和经验，不能影响安全底线**。最坏的情况是某条经验写错了，可以回滚。

**谁来改什么（用户确认，2026-10-22）**：
- 代码和硬边界（提交词表、守卫规则、新工具、图上的新节点）：只能由开发修改，改完重跑夹具。
- skill 的具体内容（某个组件怎么操作、某个平台的注意事项）：运行时由模型从过程日志（`jobs/<job-id>/run-log.jsonl`）里提出修补候选，你确认后写入。
- skill 的结构整理（新建类别、合并重复、升级为通用规则）：定期把过程日志交给开发代理做。过程日志不记填写的值、不记快照全文，可以放心交出去。
- 早期以开发为主；投递次数多了以后，以模型候选为主。

## 提交保护（系统强制，不只靠提示词）

旧流程里观察到，「立即申请」「确认意向并投递」「预览并提交」都可能直接完成提交，提交后还可能弹出安全验证。所以「Agent 不提交」必须由系统强制执行：

1. **工具白名单**：只开放导航、快照、填写、选择、上传、点击、标签页管理。不开放执行任意 JS 的工具，也不开放坐标点击。
2. **点击和按键守卫：硬边界加软边界**（`harness.policies`，用户确认，2026-10-22，取代之前「没登记过的站点首次遇到『下一步 / 保存』都先问用户」）。每次点击前，用**最新一次快照**查出目标元素的角色和名字。目标只能是快照里出现过的 ref，选择器一律拒绝（Playwright MCP 的 `target` 也接受选择器，不限制的话就能点到快照里没有的元素）。无障碍快照里看不到 `type=submit`，所以不按 `type` 判断。
   - **硬边界（写在代码里）**：名字包含提交类词（提交、投递、申请、确认、立即申请、预览并提交、确认意向、Submit、Apply、Send、Finish、Confirm 等，包括「保存并提交」这种组合），或者目标判断不了 → 拒绝，由用户自己点。岗位详情页上进入申请表的「立即申请」也算在内，由用户点进去再交回。文本框里的回车、`type` 的 `submit: true`、空格键同样拦截。词表只能由开发修改。
   - **软边界（由模型按 skill 判断）**：「下一步、继续、下一页、保存、暂存、Next、Continue、Save」之类。模型点之前必须说明用途（下一步 / 保存草稿 / 拿不准）、是否像是最后一步，以及依据（例如「进度条第 2/4 步」）。拿不准、像是最后一步、或者没给出这些说明 → 暂停问用户；用户确认过的按钮记进 `playbook/sites/<host>.md`，以后在这个站点上直接放行。
   - **其它元素**：名字不碰硬边界词表就放行（例如「上传简历」「添加经历」、链接、选项）。
3. **兜底**：每次写操作之后都重新取快照；出现安全验证、网页弹窗或疑似已提交的页面（「投递成功」「Application submitted」等）时，立即停止写操作，转人工接力，**绝不重试**。
4. **流程关卡**：图里没有任何「提交」节点。关卡 B 之后，唯一的出口是用户回报的结果。
5. **安全验证**：一旦检测到验证码、滑块、「请完成安全验证」，立即停止写操作，状态改为 `verification_pending`。用户完成后只读核验，**绝不重试提交**。

Spring AI 的工具调用设为由 Harness 自己执行，不让框架自动调用工具，这样每一次调用都要先过守卫。Spring AI 2.0.1 的做法：`ToolCallingChatOptions` 已经没有 `internalToolExecutionEnabled`，工具调用循环在 `ChatClient` 的 `ToolCallingAdvisor` 里；所以 Harness 直接调用 `ChatModel`，不用 `ChatClient`、不挂 advisor；交给模型的工具只有定义，执行一律抛异常（见 C004 总表）。

守卫按 Hermes 终端审批的结构分层（见 [research-hermes.md](../reference/research-hermes.md) §3）：
- **hardline 层**：硬边界的按钮、安全验证、网页弹窗、疑似已提交、执行脚本。没有任何模式、站点记录可以放行。
- **需确认层**：软边界按钮，模型拿不准或像是最后一步时。
- **允许名单层**：模型给出明确用途的软边界按钮、用户在这个站点上确认过的按钮，以及不碰硬边界词表的其它元素。

被拒时明确告诉模型「不要重试」。浏览器弹窗（确认框）由弹窗监督拦截后一律交给用户。子任务自动拒绝所有浏览器写操作。MCP 用 include 白名单，工具名加服务器前缀，每个 MCP 子进程只拿到它需要的环境变量。

扩展打开连接页后只等 30 秒（0.0.83 源码），超时按连接断开处理，交给用户重新同意（用户确认，2026-10-22，见 C003）。

**两种连接方式（用户确认，2026-10-22，见 C003「手动冒烟结果」）**：

| | 扩展模式（默认） | 远程调试模式 |
| --- | --- | --- |
| 启动参数 | `--extension` | `--cdp-endpoint chrome` |
| 用户要做的 | 安装 Playwright 扩展 | 在 `chrome://inspect/#remote-debugging` 打开「Allow remote debugging for this browser instance」 |
| 用户确认 | 每次连接（含重连）都由用户同意 | 开关打开期间只有第一次连接要确认，之后的连接（含重连）不再确认 |
| 能看到的标签页 | 用户交给它的标签页 | 用户已经打开的全部标签页 |
| 风险 | 小 | 开关打开期间，本机任何程序都能控制整个 Chrome，包括所有已登录的账号；用完要关掉 |

两种模式下系统都**自己新开标签页**打开岗位，只对自己新开的标签页取快照。重连或应用重启后，先重新新开岗位页，不读「当前标签页」。切换模式只改配置 `jobapply.browser.mcp.args`，不改代码。

**默认启动参数还要加上（用户确认，2026-10-22，见 C004-A）**：`--snapshot-mode none`（写操作的返回不附带快照，默认会把快照写成文件）、`--output-dir <storage>/cache/playwright-mcp`（自动生成的文件，包括 console 日志，都写在这里，每次建立连接和关闭时清空）、`--console-level error`、`--image-responses omit`、`--no-webmcp`（不收集网页自己注册的工具）。MCP 客户端声明 root 为 `storage/uploads/`，所以能上传的文件只限于这个目录。

后端通过 Spring AI `spring-ai-starter-mcp-client`（2.0.1）以 stdio 方式启动 MCP。

旧流程有「单步回退 Computer Use」。新系统**不做**这个回退，受阻的那一步改为人工接力，由用户自己操作。

## 登录状态

原则：**系统不保存、不读取、不输入密码，也不读取、导出 Cookie 或 Token。**

- **已确认（2026-10-22）：直接使用本机的 Chrome**，不另建专用资料目录。默认通过 Playwright 扩展连接，**第一次连接时由用户同意一次，连接断开后重新同意一次**；远程调试模式下只有第一次连接要确认（见「Chrome MCP · 两种连接方式」）。登录状态就是你平时 Chrome 里的登录状态。
- 因为用的是你日常的浏览器，Agent **只操作它自己新开的标签页**，不读取、不切换到其它标签页。白名单里没有切换和关闭标签页的工具；系统新开的标签页由用户自己关。
- 每次申请打开页面后都先交给你登录（见主流程），所以不再需要「登录预检」。
- 浏览器全局只有一个，所有 Project、所有 Session 的浏览器任务共用**同一条串行队列**。搜索和抓取不走浏览器，可以并行。
- 每次打开申请页后，检查是否被重定向到登录、SSO 或验证码页面。是的话进入接力，状态改为 `needs_login`。
- **登录与身份由模型判断（用户确认，2026-10-22，从里程碑第 3 段起）**：用户说「好了」之后，由模型读快照，判断是否已经登录、登录的是不是正确的账号；拿不准就问用户。关键词识别（C003 的 `LoginPageDetector`）只作为给模型和用户的**提示**，不拦流程。注意：很多招聘网站登录后不跳转，只是在右上角多出头像、名字、「我的投递」「退出登录」之类，所以不能靠「URL 变了」或「登录框消失了」来判断。
- 身份核对：同一个站点可能有多个账号。切换账号或关闭标签页后，丢弃旧的 ref，重新核对当前身份和官方历史。
- `browser/sites.md` 记录：站点、账号标识、最近一次确认已登录的时间、状态。**账号标识可选，由用户自己填写**（用户确认，2026-10-22）：各个站点的登录方式不同（邮箱、账号密码、公司自家的社交 app 等），所以 UID、用户名、邮箱、手机号都可以，也可以留空。不写密码。
- 不替用户注册账号；遇到注册页就转人工接力。

## 岗位搜索（Web Search）

旧流程主要投国内校招和外企中国区，所以搜索要以**招聘门户类型**为单位来设计，不能假定都是 Greenhouse / Lever。

1. **数据源登记**（按招聘系统写在 `playbook/skills/platforms/<name>/SKILL.md`，公司自建站写在 `playbook/sites/<host>.md`，同时写明搜索方式；2026-10-22 随 Playbook 结构调整）：
   - 公司自建校招站、Moka 系、飞书招聘系、外企 Job Cart 站：用 `site:` 搜索，加上公司官网的入口。
   - 学校就业平台转载的官方简章：只作为线索，最后要回到官网核实。
   - Greenhouse / Lever / Ashby：直接调公开接口（已验证可访问）。
2. **搜索**：搜索层根据 Project 偏好生成搜索词。**国内站点在 Brave、Exa 等搜索引擎里的覆盖情况未知，施工时要先实测。**
3. **核实**：搜索层抓取页面。国内招聘站多是 SPA，抓取可能拿不到内容，这时改为浏览器只读读取（进入浏览器队列）。
4. **入库**：按「公司 + 招聘项目 + 岗位 ID」去重，写入 Project 的候选池（`jobs/<job-id>/job.md`，`lead_status: new`）。区分「岗位族」和「具体在招岗位」：只找到岗位族的，标为「监控」。

### 三种接法的区别（回答用户的问题，2026-10-22）

「Search MCP」「我们自己搜」「Hermes 的网络搜索」**底层都一样**：都是调用第三方搜索服务（Brave、Tavily、Exa、Firecrawl、Parallel 等）的 API，都需要那家的 API key。区别只在**调用代码放在哪里、谁能控制它**：

| 接法 | 是什么 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. Search MCP** | 厂商或社区提供的 MCP 服务器（Node 子进程），后端通过 MCP 协议调用它 | 不用写调用代码；换一家只需要换一个 MCP | 多一个子进程；返回什么、怎么截断由别人决定；我们的 URL 检查、限速、缓存只能套在外面 |
| **B. 后端直接调 API（自研）** | Java 后端用 HTTP 直接调搜索 API | 只多一个 HTTP 调用，没有额外进程；结果格式、截断、缓存、限速、URL 安全全部在我们手里；方便写确定性测试 | 每接一家，要写一个小适配器（一般几十行） |
| **C. Hermes 的 `web_tools`** | Hermes（Python）内部的函数，用的就是 B 的做法：直接调 firecrawl / tavily / exa / parallel 的 API，再用辅助模型摘要长页面 | 设计已经验证过，可以照着做 | 是 Python，不能直接嵌进 Java 后端；要用的话得把 Hermes 当成一个独立服务来跑，太重 |

### 已确认：分层 Web 工具（Web Tool Router，用户确认，2026-10-22）

采用 B（后端直接调 API），并按 Hermes 官方文档描述的分层与省钱做法来设计（[文档：Web Search & Extract](https://hermes-agent.nousresearch.com/docs/user-guide/features/web-search)、[Browser Automation](https://hermes-agent.nousresearch.com/docs/user-guide/features/browser)，2026-10-22 查阅；本机 0.12.0 源码与文档有差异，以文档描述的较新做法为参考）。**不引入 Hermes 本身。**

```text
Agent（Spring AI Tool Calling）
   └─ Web Tool Router（自研，Java）
        ├─ search   发现信息   → 免费来源优先 → 额度用完或被限流时切到 Brave（填了 key 才启用）
        ├─ extract  读取正文   → 后端直接抓取 + HTML 转 Markdown（如 Jsoup），不启动浏览器
        ├─ browser  登录、点击、填表、SPA 页面 → Playwright MCP（连接本机 Chrome）
        └─ cache    结果复用   → 搜索结果、正文抽取结果
   所有请求先过同一层检查：URL 安全、域名策略、限速
```

**原则：能用 search / extract 解决的，不启动浏览器。** 浏览器只用于需要登录、页面交互，或者 extract 拿不到内容的 SPA 页面。

| 层 | 设计 | 成本控制 |
| --- | --- | --- |
| search | `SearchProvider` 接口，结果统一为 `{title, url, description, position}`，默认 5 条。**提供方按链式顺序尝试**：先用免费来源，被限流、额度用完或没有结果时，切到下一个；最后是 Brave。Brave 的 key 在设置页里**可填可不填**；不填时，免费来源都失败就告诉你，不硬撑 | 不花钱优先；结果缓存 |
| extract | 后端抓取，转成 Markdown。返回给模型的正文**默认上限约 15,000 字符**；超出时保留开头约 75%、结尾约 25%，加上「已截断」说明；**全文存成文件**，模型需要时再按段读取。默认**不调用模型做摘要**（省 token）。JD 的资格条款从全文里定向读取，保留原文 | 少送 token；不启动浏览器 |
| browser | Playwright MCP，`--extension` 连接本机 Chrome。快照用文本化的无障碍树加 ref，**不在每一步都传截图** | 少传图片；不用付费云浏览器 |
| cache | 搜索：同一查询（忽略大小写和多余空格）短期缓存。抽取：全文存在 `storage/cache/web/`，**所有 Session 和子任务共用**（多个子任务查同一家公司时，不重复付费、不重复抓取）。只缓存成功的结果；TTL 可配置（默认 20 分钟，范围 1 分钟到 1 天）；投递状态页这类实时页面不缓存 | 减少重复搜索和抓取 |

**免费来源**（具体用哪些，施工第 4 段实测后再定，尤其要测国内招聘站的覆盖）：
- **SearXNG**：本机用 Docker 自建（本机 Docker 已可用），免费、没有额度限制，可以聚合多个搜索引擎；
- **DuckDuckGo**：不需要 key，但稳定性一般；
- 各家的免费额度：例如 Brave 免费档每月 2,000 次（Hermes 文档所载），以及 Exa、Firecrawl、Tavily 的免费档。是否轮换使用，施工时按各家条款决定。

**为什么浏览器还是用 Playwright MCP，而不是 Java Playwright**：
- Java Playwright 连接你自己的 Chrome，只能走 CDP 远程调试端口；新版 Chrome 不允许对默认资料目录开这个端口，就得另建资料目录，和「直接用本机 Chrome」的决定冲突。
- Playwright MCP 的扩展模式可以直接连接本机 Chrome，并且由你在 Chrome 里同意连接。

**不借鉴**：Hermes 较新版本默认的 Browser Use 模式是让 Agent 自己写 Python 代码去操作浏览器。JobApply 不允许这样做，因为能执行任意代码，就能绕过「不点最终提交」的守卫。

**安全检查**（所有 search / extract / browser 导航都要经过）：
- 内网、回环、云元数据地址拦截，DNS 失败也拦截；
- 带疑似密钥的 URL 一律拒绝；
- 域名黑名单（含「禁止自动化站点」），重定向后再查一次；
- 按域名限速。

不做：不用浏览器去 Google、LinkedIn、BOSS 上自动搜索（有验证码，条款也不允许）。在这些地方看到的岗位，用户手动粘贴链接。

## 状态：阶段 + prep 子状态 + 轮次

投递之后的流程因公司而异，所以状态拆成固定的**阶段**（`prep → applied → screening → assessment → interview → offer → closed`）和可变的**轮次**列表。详见 [tracking.md](tracking.md)。

`prep` 阶段内部的子状态（`prep_state`）：

```text
discovered → matched → selected → preparing ──→ awaiting_review → user_submitting
               ↘ skipped / monitoring   ↕                     ↘ verification_pending
                                needs_input / needs_login / handoff_user / failed
user_submitting / verification_pending → 有证据 → phase=applied；只有口述 → unconfirmed
任意未提交状态 → paused（用户暂停或转到下一家公司）
```

补充规则（C002 起草时提出，用户确认，2026-10-22）：
- `discovered`、`matched`、`skipped`、`monitoring` 与候选池的 `lead_status` 重叠。转为申请之前只用 `lead_status`；转为申请后，`prep_state` 从 `selected` 开始。「监控」怎么表示，到里程碑第 4 段再定。
- `awaiting_review` 可以回到 `preparing`（关卡 B 时用户要求修改）。
- `paused` 恢复时只能回到 `selected` 或 `preparing`，恢复后先只读核对页面。
- `user_submitting`、`verification_pending` 不能转为 `paused`，因为提交可能已经发生了。
- `unconfirmed` 补到证据后可以进入 `applied`。
- `closed` 是终态；暂不支持重新打开。

- 从 `prep` 进入 `applied` 的唯一条件是有证据：成功页或官方历史记录。
- 官网的「暂不匹配」等原文要保留在结果里。
- 通知是否送达单独标注，默认为「未确认」。
- 投递之后，各轮的结果大多来自用户告知，要标注 `result_source`。

## 预算与停止条件（用户确认放大，2026-10-22）

用户指出：Playwright 的调用次数会很多，岗位调研也是。所以预算放宽，而且**用「软上限 + 问你是否继续」代替硬性失败**。真正要拦住的是「原地打转」，不是「做得多」。

### 两种上限

- **软上限**：到了就暂停，告诉你用了多少、做到哪一步，问你是否继续。你同意后再给一轮同样的额度。不会丢进度。
- **打转检测**：不看总量，看是否在重复。命中就**立即**停下，转人工接力。

所有数字都可以在设置页修改。

### 单个申请（申请线程）

| 项 | 默认值 | 说明 |
| --- | --- | --- |
| 每个页面的工具调用 | 软上限 **120** 次 | 一个长表单页会有大量快照、填写、选择、上传 |
| 整个申请的工具调用 | 软上限 **600** 次 | 多页表单、在线简历补全、上传多个附件 |
| 整个申请的 token | 软上限 **300 万**；到 80% 时提醒一次 | 快照是主要消耗 |
| 同一个元素连续失败 | **5** 次 → 转人工接力 | 打转检测 |
| 相同操作得到相同结果 | 连续 **4** 次 → 停下 | 打转检测，例如反复点同一个按钮页面没有变化 |
| 页面没有任何变化 | 连续 **10** 次操作 → 停下 | 打转检测 |
| 无人响应的等待 | 关卡和接力**不设超时**，一直等你 | 申请线程挂起，不占模型调用 |

### 一次调研（Session 里的 research 任务）

| 项 | 默认值 | 说明 |
| --- | --- | --- |

| 相同查询或相同 URL | 命中缓存，不重复计费 | |

### 降低消耗的做法（与预算配套）

- 快照尽量只取变化的部分，或者只取当前表单区域，不在每一步都取整页快照；超长快照写进文件，只给模型预览（参考 Hermes 大输出落盘）。
- 已确认的字段在一次调用里批量填写（Playwright MCP 的表单批量填写），不逐个字段调用。
- 页面变化后才重新取快照；没有变化就复用上一份。
- 调研阶段的 JD 正文只给截断后的版本，全文按需再读。

用量按申请、按 Session、按 Project 统计，在 Job 详情和 Session 视图里显示。
