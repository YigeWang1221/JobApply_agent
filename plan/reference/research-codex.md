## 2. 被反复验证、应当保留的原则

1. **证据优先于口述和旧记录**。「已提交」只认官网成功页或官方投递历史；用户口述、旧准备日志、进入申请页都不算。旧日志追加纠正，不静默覆盖。
2. **授权按岗位/批次，不外溢**。一次授权只覆盖明确列出的岗位或批次；新岗位、改材料、新出现的敏感/法律问题要重新确认。已确认的同一事项不重复问。
3. **字段分级**：普通事实可按档案填写；个人信息（姓名、联系方式、照片、精确日期）需用户核对；敏感/法律字段（证件、工作授权、签证担保、人口统计、健康、薪资、法律声明）**永不预设、永不入通用档案**，由用户逐项确认或亲自填写。
4. **单次答案不升级为默认**。某次表单里的专业写法、城市排序、志愿选择、声明同意，只属于那一次申请。
5. **原件不可改**。简历原件内容与排版只由用户改；代理只能提建议，或制作重命名的等字节副本（SHA-256 校验）。
6. **MCP 优先**：通过 DOM / 无障碍树操作；只有单个元素经合理尝试仍受阻时才回退（旧系统回退 Computer Use），完成后立即回到 MCP。保留已认证会话，不重置浏览器、不清数据、不读 Cookie / Token。
7. **查询与操作分离**：公开信息（公司介绍、校历、招聘简章）用 Web Search；已登录表单、实际选项、申请状态用浏览器 MCP。
8. **精简执行**（2026-09-28 后的「一次」原则）：一次恢复状态、一次读完整 JD、一次集中问答、批量填写、一次最终审核、一次结果核验、一次回写。目的是控制 token 与操作次数。
9. **来源优先级**：公司官网 / 职位详情 > 学校就业平台转载的官方简章 > 其他。未披露的薪资、截止日期写「未披露 / 待核实」，不推算。

## 3. 浏览器操作的实测坑（站点无关，进入通用 Playbook）

**提交边界**
- 「立即申请」「确认意向并投递」「预览并提交」「Apply」都可能直接完成提交。**不能用按钮试探**它是否只是进入详情或预览。曾观察到某社招入口点「立即申请」后直接显示申请成功。
- 点击提交后可能弹出安全验证（滑块、验证码）。出现时提交请求**可能已经发出**：立即停止写操作，交给用户；用户完成后只读核验，绝不重试提交。
- 用户完成验证后可能自动提交，此时不能再承诺可以修改材料。

**状态与保存**
- 「输入成功」「点了选项」不等于「已保存」：要保存后刷新或重新进入页面回读。
- 「在线简历保存」和「岗位申请提交」是两件事，分别核验。
- 页面一变，旧的元素 ref 就失效；每次页面变化都要重新取快照。
- 超时先读当前 URL 和主内容，判断操作是否实际成功，再决定下一步；不盲目重复。

**简历解析与上传**
- 上传主简历后，站点解析会**回填并覆盖**已填字段（邮箱、学校、日期、项目）。顺序必须是：先上传 → 等解析结束 → 再校正字段。
- 解析常见错误：同名学校被识别成国内另一所学校；区号识别错；学校城市识别错；日期偏移一天或一个月；项目经历整段遗漏；旧版学位名称被带入。原因未查明，**只能校正为档案值，不能自行加减日期**。
- 「同步更新在线简历」类选项可能让解析覆盖人工整理的内容，可在授权内关闭并核验勾选状态。
- MCP 上传路径受限时：把原件复制到允许目录，校验哈希一致后上传，不转换格式。
- `setFiles` 成功只代表选中了文件；要等「上传中」消失，回读每份附件的文件名、大小和完成状态。刷新后附件可能丢失，需要重新检查。
- 有的附件栏一条只能挂一个文件，多份 PDF 要新增多个条目，逐个上传、逐个核验。

**控件**
- `role=combobox` 可能其实是文本搜索框（用 fill），也可能是只读下拉框（用选项操作）；看实际元素类型。
- 多选城市以「已选标签」核验，输入框为空不代表没选。分组标题（如某个市）点一下可能只是展开，要再选组内条目。
- 下拉框已显示选中值，但仍残留必填错误时，聚焦后按 Tab 触发失焦校验。**不要把提交按钮当校验工具。**
- 同名链接、加号按钮要限定在对应区域里，不用全页 nth-of-type 猜位置。
- 报 `elementHasNoFrame` 时先滚动到可视区域。
- 日期控件直接输入可能写进错误字段，用日历控件更稳。

**人工接力**
- 用户正在编辑、上传或切标签时，代理停止写操作；用户交回后先只读当前状态（URL、保存状态、附件、已选标签、校验提示），不覆盖用户填的内容。
- 用户说「填好但没提交」时，以官网历史为准，曾出现官网已显示提交的情况。
- 多个文件选择窗口要逐个确认来源，不盲目批量取消。
- 不要让用户和代理同时操作同一个表单或同一个浏览器焦点。

**账号**
- 同一站点可能有多个账号（邮箱注册、手机/微信绑定），历史与额度可能跨账号累计，也可能不累计。切换账号后要重新列标签页、刷新，核对当前身份与官方历史。
- 账号绑定邮箱、申请表联系邮箱、简历内邮箱、最终预览邮箱、通知邮箱是**五个不同的东西**，要分别记录；未见证据就写「未确认」。
- 看到「Sign in」字样不一定是已退出登录，要看可见的账户状态。

## 4. 筛选与匹配的经验

- **资格逻辑保留原文**：`学位 AND 2+ 年经验 OR equivalent experience` 不能简化成「要求 2 年」。区分三档：明确符合；方向匹配但等效经验待招聘方判断；明确缺少硬条件。
- **JD 与实际筛选题分开核实**：表单里的问题可能比 JD 更严格（例如去掉了 equivalent），要逐题如实回答。
- **硬门槛**：工作年限（3+ / 5+ 年）、职级（Senior/Staff/Principal）、核心语言（如 C++）、在读身份 / 毕业窗口 / 届别、地区批次。不为凑额度投硬门槛不满足的岗位。
- **评分模型**（旧研究表 v3）：`Apply Score = 30% 方向匹配 + 40% 核心技能 + 18% 级别匹配 + 12% 资格匹配 − 硬门槛罚分`，并带置信度。只按**现有证据**打分，计划中的项目只算潜在加分。
- **降级替代**：高级岗不进 P0，改找同公司 Junior / Graduate / Intern 替代岗；原岗只作技能标杆。
- **岗位族 ≠ 在招岗位**：只找到岗位方向、没找到具体在招岗位时，只列入监控，不算 P0。
- **薪资证据分类**：岗位官方、公司级总包、市场指南、模型估算，四类不能混用。
- **曾用两个模型交叉核验研究表**，发现了单个模型漏掉的高性价比入口和评分误判。可作为可选步骤。
- 简历版本按岗位方向映射（如云/后端版、AI/LLM 版）。映射只给出候选，最终要按实际 JD 核对。

## 5. 额度与招聘项目

- 很多国内校招有投递额度：每集团 N 个志愿、3 个月内 N 个职位、每批次 N 次，有的提交后不可修改，同一招聘项目可能只允许投一次。
- 额度以官方页面提示为准；看不到就写「未核实」。不能从「已投 N 个」「第 N 志愿」反推上限，也不能把一家公司的规则外推到另一家。
- 被拒记录是否继续占用额度要实测，不要假设。
- 绝不另建账号来规避额度。
- 规划多投之前，先查官方历史和额度，避免重复投递。

## 6. 站点类型观察（每次仍需按当前页面核对）

| 站点类型 | 观察到的流程特点 |
| --- | --- |
| 大厂自建校招站（意向购物车式） | 岗位详情 → 加入意向 → 选志愿、业务线、城市、调剂城市 → 「确认意向并投递」进入在线简历 → 审核附件和字段 → 勾选声明 → 「投递简历」最终提交；成功页 URL 带 success 标记 |
| 外企自建站（Job Cart 式，英文） | 支持一次申请多个岗位；表单中有独立的资格题、工作授权、自我认同、多项 Acknowledgment；历史页有 Submitted 标签 |
| Moka 系校招站 | 在线简历与岗位申请分开；有「同步更新在线简历」选项；「预览并提交」后有「确认提交」，之后可能弹出安全验证；历史页按志愿排序 |
| 飞书招聘系 | 校招和社招分开入口；有官方应聘记录页；额度按批次计算 |
| 招聘 App 网页版（BOSS 类） | 出现过 close/back 机制，触发原因未查明 |
| 国内社招入口 | 「立即申请」可能一键提交 |

站点的 SPA 页面多，公开岗位列表常需要 JS 渲染。

## 7. 旧系统的痛点（新系统要解决的）

1. **没有单一事实来源**：同一段「核验更新」被原样粘贴进日志、多个申请记录和交接文件；台账有 Numbers、两种不同列的 CSV、xlsx、json 五种格式，需要「按 Job ID 去重同步」。→ 新系统里每个申请只有一个结构化记录，台账和导出都由程序生成。
2. **「最新状态优先于下方早期过程」**：记录文件越写越长，新旧状态混在一起，要靠标题声明哪段作数。→ 新系统里当前状态是字段，历史写进追加式事件日志。
3. **手动备份**：没有 git，每次改流程都要整目录复制备份。→ 新系统里 `storage/` 用独立的本地私有 git 仓库。
4. **规则文件膨胀**：`WORK_BY_STEPS.md` 每次复盘都追加章节，有重复（同一段复盘补充出现在两个文件里），通用规则和站点特例混在一起。→ 新系统把 Playbook 分成通用和站点两层，每条带观察次数和最近验证日期，由程序合并去重。
5. **代理在得到授权后曾代为点击提交**。新系统改为最终提交一律由用户完成。旧经验里「提交后核验」的部分仍然适用，只是变成核验用户的提交。
6. **跨天恢复靠手写交接文件**。→ 新系统用 LangGraph4j 持久化 Checkpoint 加待办视图。
7. **时区**：本地是美东时间，官网显示中国日期，两者不一致，要同时记录。

## 8. 旧系统的 APPLICATION_STATE 最小模板（新系统的 Graph State 参考）

公司 / 站点 / 招聘项目；岗位名、ID、城市、类型（校招·全职 / 实习 / 社招）；官方链接、历史页链接；资格结论与差距；额度规则与证据；选用材料（原件路径、上传名、哈希）；当前 URL 与步骤；已确认答案与未确认项；材料审核与授权范围；成功证据与官方状态；待同步事项。
